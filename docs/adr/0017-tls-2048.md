# ADR-0017: 2048-bit TLS identity + weak-key rotation (fuzz finding)

## Status
Accepted (extends ADR-0010; no prior ADR modified)

## Context
The host fuzz bench (`scripts/fuzz-mcp.py`, stdlib Python `ssl`) could not
complete a TLS handshake: the server presented a 1024-bit RSA self-signed cert
(Ktor `buildKeyStore` default), which OpenSSL security level ≥ 2 aborts with
"EE certificate key too weak". curl worked only because its default security
level still tolerates 1024-bit keys. Any modern agent stack (Python, newer
Android/Conscrypt) would fail the same way — a real interop/hardening bug, not
a bench artifact.

## Decision
- Pin `keySizeInBits = 2048` in `TlsStore`'s Ktor certificate builder (SHA-256
  pin from ADR-0010 stays).
- Fail closed on load: `TlsStore.loadOrCreate()` rotates any stored identity
  whose public key is missing, non-RSA, or RSA below `McpHttp.MIN_TLS_RSA_BITS`
  (2048). Rotation invalidates the old TOFU pin; the dashboard shows the new
  fingerprint (TOFU re-verify once, per ADR-0010).
- Pure, JVM-tested seam: `McpHttp.isTlsKeyTooWeak()` + `TlsKeyStrengthTest`
  (1024 weak / 2048 accepted / null + EC weak).

## Consequences
Positive: handshakes succeed at OpenSSL seclevel 2; key strength matches
current minimum guidance.
Negative: one-time pin rotation for existing installs (fingerprint changes;
agents must re-verify). 2048-bit RSA handshake is marginally more expensive —
negligible for a LAN control plane.
